# Engine support

runskein bundles adapters for OpenCode, Kimi Code, Claude Code, Codex, and
pi. An adapter makes an engine discoverable; it does not make every
engine-specific protocol feature universally available. Consumers should use
the capability tier and runtime discovery rules below when choosing an engine
or enabling an optional feature.

## Capability tiers

| Tier       | Consumer contract                                                                                                                              | How to use it                                                                                                               |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Core       | Available through runskein on every registrable adapter; a failed Core gate prevents registration.                                             | Call it directly and handle its documented typed errors.                                                                    |
| Negotiated | Available only when the selected engine advertises the capability. An absent capability raises `NotSupportedError`; runskein never ignores it. | Read `hub.describe(id).capabilities` before designing a dependent flow, and handle `NotSupportedError` for runtime changes. |
| Emulated   | runskein supplies the behavior when the engine lacks the native protocol feature.                                                              | Call it directly, then inspect the returned result when it records the path taken, such as `session.resumeTier`.            |

Core describes runskein's contract, not an assertion that a local binary is
installed or authenticated. `hub.engines()` supplies those local facts; an
engine with `health: 'not-installed'`, `health: 'unauthenticated'`, or
`health: 'invalid'` is not usable for a new session.

## Discover capabilities at runtime

Use inventory for local availability and a descriptor for the selected
engine's live protocol surface. `engines()` does not spawn a process;
`describe()` does, so cache or reuse the descriptor when a user interface
renders it repeatedly.

```ts
import { createHub } from 'runskein';

const hub = createHub();
const engines = await hub.engines();
const codex = engines.find(
  (engine) => engine.id === 'codex' && engine.installed && engine.authenticated !== false,
);

if (!codex) throw new Error('Codex is not installed or is not authenticated.');

const descriptor = await hub.describe(codex.id);
if (!descriptor.capabilities.session.fork) {
  // Select a no-fork workflow before creating a session.
  console.log('This Codex installation does not advertise session/fork.');
}
```

Capability discovery is a preflight, not a replacement for error handling. A
CLI update or a failing engine can still make a negotiated call reject with
`NotSupportedError`; handle that error at the call site.

`EngineDescriptor.capabilities` is the public normalized capability map:

| Field         | Examples                                                          |
| ------------- | ----------------------------------------------------------------- |
| `loadSession` | Native history loading is advertised.                             |
| `session`     | `resume`, `fork`, `list`, `delete`, and other session operations. |
| `prompt`      | `image`, `audio`, and `embeddedContext` inputs.                   |
| `mcp`         | `http` and `sse` MCP transports.                                  |
| `providers`   | The engine supports provider discovery.                           |

The map is intentionally open-ended: new normalized capability keys can
appear as the underlying protocol evolves. Treat an absent key as unsupported,
not as an error.

## Measured built-in support

Which of these capabilities each bundled engine actually advertised, at the
version it was probed at, is a generated table:
**[capability-matrix.md](capability-matrix.md)**. It also carries the tier and
API for every feature, so it answers "can this engine do X" and "what happens
when it cannot" in one place.

It is a snapshot of one probe run, not a compatibility promise for every CLI
release. For what the machine you are running on has, use `hub.engines()` and
`hub.describe()` as described above — those are the runtime facts, and the
ones a program should branch on.

## Keeping this page current

The raw matrix is generated by the real-engine probe:

```sh
pnpm --filter @runskein/conformance probe
```

The probe writes `docs/conformance/matrix.json`, which is not published — it
records the provider configuration of whichever machine ran it. What the tables
read is a projection of it, so refresh that next, then the tables:

```sh
node scripts/project-conformance-matrix.mjs --write
node scripts/generate-capability-tables.mjs
```

Refresh all three in the same change whenever a supported engine's observable
capability, detection result, supported version, or capability tier changes.
`pnpm quality` checks both steps wherever the raw matrix is present, and the
projection is the one that fails first — a regenerated table over a stale
projection is still stale. Where it is absent, neither can be checked: the
projection step reports that it has nothing to compare and exits clean, so a
green run there says nothing about whether these tables are current.
Do not infer a new row from adapter metadata alone: runtime probe output is
the source for negotiated capabilities.

For full API types, error contracts, and lifecycle behavior, see the frozen
[API specification](engine-adapter-api.md).
